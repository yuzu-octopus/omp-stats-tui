# Screenshot-driven dashboard composition

## Problem

The user's twelve Windows Terminal screenshots invalidate the previous visual acceptance. The dashboard is a linear report stretched across a fullscreen frame: unreadable dim-purple secondary text, metrics clustered at the top-left, oversized solid bars for two buckets, far-separated legends, repeated hints, and sparse lists surrounded by unused space. Functional verification did not establish visual quality.

## Design

- Keep current omp theme, but use readable `text`/`muted` for content. Reserve accent and semantic colors for selected state, significant values and actual measured series. Do not paint ordinary metadata in the low-contrast structural `dim` color.
- Full-width metric-card rows with rounded native borders, consistent padding, bold values and short readable hints. Four figures fit one wide row; six use two rows of three rather than tiny boxes with truncated labels. Narrower terminals balance fewer cards per row.
- Compose actual dashboard widgets into framed, titled panels. Wide screens place charts beside tables/breakdowns; narrow screens stack the same widgets. Equal-height framing clarifies layout without fabricating content. Retained controllers still own input, focus, selection and details.
- Bound time-series marks independently of bucket spacing. Two daily buckets must be two narrow bars, not two half-screen rectangles. Keep empty buckets, null gaps, correct units, UTC timestamps and selected values; pair charts with compact legends rather than pinning values to a distant screen edge.
- Use real measured distributions/rankings and selected-record summaries to give sparse tables context. No fake metrics, no animated fake data, no paid calls. Empty Gain/Frustration states need a purposeful explanation and actionable real controls.
- Preserve all twelve route workflows, price floors/unpriced counts, independent quota reads, nested traces/minimap, search and explicit paid authorization.

## Review gates

1. Review the actual visual surface at the user's approximate wide aspect, plus 100/40 columns.
2. Sparse-data fixtures are required: two buckets, one model, two projects, four failures, empty Gain, under-threshold Frustration. Large fixtures alone hide composition defects.
3. Readable secondary labels, bounded marks, useful panel composition, explicit focus and no distant legend values.
4. Exercise keyboard/search/detail/close behavior after the visual cutover; build, types and full behavioral suite after edits settle.
5. Publish evidence without private history/screenshots or claims that passing tests make an interface beautiful.

## Execution and evidence

- All twelve retained controllers now use the shared composition where applicable. Trace timelines remain unframed; nesting, viewport and hit geometry are unchanged.
- Actual `TUI`/`ProcessTerminal` fullscreen mounting exercised all twelve routes with sparse fixtures at 150×38, then resized through all routes at 100×38 and 40×38. A separate populated run exercised all twelve routes, including both Gain histories and populated frustration rates.
- Visual review used captured ANSI terminal state rendered into images with DejaVu Sans Mono outlines, not a separate mock UI. This verifies composition and active amethyst-theme ink; it does not reproduce Windows Terminal's font rendering or translucent background.
- Sparse review covered two native buckets, one model, two projects, four failures, empty Gain and below-threshold frustration. It exposed tiny six-card rows and indistinguishable long project prefixes; those were corrected and re-exercised.
- Mounted search/project detail, lazy request inspector, JSON expansion, analytics pane focus and overlay close were observed. A separate unmodified reader run settled a real worker-backed empty dashboard and live status in an isolated HOME. No broker credentials or paid judge action were used.
- Final distribution also mounted through `/stats-tui` inside compiled omp 18.6.1 with its active dark theme: Overview → Requests, 150→100-column resize, live worker status and close back to the editor were observed. First-run setup was exited without authentication; no model prompt was sent.
- Integrated behavioral suite: **894 pass, 0 fail**, 61 files, 102,931 assertions. Source-text scanners and incidental footer/legend wording assertions were removed rather than re-pinned; consumer boundary regressions cover sparse marks, hidden numbers, wrapping and Windows project identities.
- Final `bun run build`, default full TypeScript `--noEmit`, and `bun run verify:patch` all succeeded.
- Published as [dashboard composition PR #3](https://github.com/yuzu-octopus/omp-stats-tui/pull/3), rebased onto the merged PR #2 baseline. Review checkout: `omp/dashboard-composition` on the approved fork.
